# v0.7.0 Sprint Close — Architecture patterns and learnings

## Scope

Epic CAC-E03: 8 tickets (CAC-007 through CAC-014), all completed 2026-04-01.

## Architectural Patterns Established

### 1. Module-level registry for connection reuse

All 4 backends (DiskCache, Redis, MongoDB, Postgres) use the same pattern:
- `_client_registry: dict[str, T]` keyed by connection URL
- `_ensured_*: set[tuple[str, str]]` for DDL/index deduplication
- Check registry before creating → reuse or create+register

This pattern emerged in v0.6.0 (MongoCache) and was replicated consistently in v0.7.0.

### 2. CacheProtocol with positional-only `/`

Positional-only parameters in `CacheProtocol` enable structural subtyping —
parameter name differences (e.g. `key` vs `name`) don't break protocol satisfaction.
This was validated with mypy during CAC-007.

### 3. DURL self-describing serialization

The most important design in v0.7.0: compression metadata lives in the Data URL
parameter (`compression=zstd`), not in the Cachetic instance config. This means:
- Reader doesn't need to know writer's settings
- Cross-config reads work (compression=True writer → compression=False reader)
- Legacy data (pre-v0.7.0) is auto-detected by absence of `data:` prefix

### 4. 3-path detection in `_loads_any`

```
data: prefix → DURL parse → extract compression from parameter
zstd/zlib magic bytes → legacy compressed → decompress
else → raw bytes/JSON → direct validate
```

Backward compatibility is achieved without any migration step.

## API Gotchas

### peewee 4 psycopg3 auto-detection

peewee 4.0.3 dropped `playhouse.psycopg3_ext` — `Psycopg3Adapter` is now built
into the main `peewee` module. `PostgresqlDatabase` auto-detects psycopg3 at runtime.
Don't import from `playhouse.psycopg3_ext`; it doesn't exist in v4.

### peewee dynamic model + Meta.table_name

When creating a Model class inside a factory function, `Meta.table_name = table`
works because Python evaluates the RHS in the enclosing function scope, not the
class scope. No `nonlocal` or other tricks needed.

### MongoCache `ex` field vs PostgresCache `expires_at`

MongoDB `ex` field stores Unix timestamp despite the API `ex` parameter being
duration (seconds). This is legacy naming — not worth migrating. Postgres uses
`expires_at` (clear timestamp semantics). Both convert duration→timestamp internally.
